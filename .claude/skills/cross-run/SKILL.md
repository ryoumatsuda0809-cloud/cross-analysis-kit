# cross-run ｜ クロス分析の司令塔

## このスキルが存在する理由

①〜④の4スキルは既にある。**足りないのは、それらを正しく並べて回す仕組み。**

実走で分かったこと（→ 3-17）：

> **`03_仮説_封.md` を書いたAIが、同じ会話で②を実行すると、Read しなくても中身を知っている。**
> genba-ops SKILL.md の「②は `03` を読まない」は、**②が別コンテキストで動く前提**だった。
> 1本の会話では成立しない。

つまり——

> **「読まない」は運用ルール。「知らない」は構造。守れるのは後者だけ。**

このスキルは、その構造を毎回手で組まなくて済むようにするためにある。

---

## 前提：クロス分析の成立条件（見失わない）

**外の事実（A軸）× 現場の現実（B軸）→ 真因。**

| 条件 | 内容 | このスキルでの実装 |
|---|---|---|
| ① 違う盲点 | 同じ盲点の2つを足しても意味がない | A軸にB軸の仕事をさせない |
| ② **独立に取る** | 先に見た答えに人は引きずられる | **`03` の封＋サブエージェント隔離** |
| ③ 食い違いを潰さない | どちらが正しいかで決着させると価値が消える | ③に「決着させるな」を明示 |
| ④ 意味は人間が決める | 矛盾の意味は文脈が要る | 「現場で確認すべき点」を必ず残す |

条件②の根拠は自動化バイアス（Dratsch 2023）。AIの誤った提案を先に見せると、
**専門家の正答率が 82.3%→45.5%、新人は 79.7%→19.8%** に落ちる。

**AIの仮説を読んでから現場に行った人は、もう独立した2つ目の情報源ではない。**

## パイプライン（順序が意味を持つ）

```
案件/{会社名}/
  _材料/A_公開/取得ログ.md   ← ①が残す生の材料（捏造の検出用）
  01i_外形カード_内部用.md   ← ① market-recon ★定規。②③④が読む本体
  01_外形カード_事実編.md    ← ① 〃 01iから起こす提出用 ┐ 現場に持って行く
  02_現場で確認すべき問い.md  ← ①              ┘ ★01は現場前に凍結
  03_仮説_封.md              ← ①              ★封
  _材料/B_現場/現場メモ.md   ← 人間が現場で取る（gitignore）
  04_現場分析.md             ← ② genba-ops   （★03も02末尾も見ない）
  05_反証レポート.md         ← ③ shinin-hansho（★04→01→02→03の順。中身は司令塔がプロンプトに埋め込んで渡す）
  06_課題仮説レポート.md     ← ④ tougou-report（05の格付けのみ。03を読まない）
```

### 誰が何を見てよいか

| | `01` | `02` 本文 | **`02` 末尾の見立て** | `03` | `04` |
|---|---|---|---|---|---|
| ① market-recon | 作る | 作る | — | 作る | — |
| **② genba-ops** | ✅ | ✅ | **❌ 見ない** | **❌ 絶対に見ない** | 作る |
| ③ shinin-hansho | ✅ | ✅ | **✅ 見てよい**（3つ目の視点） | **✅ 開封する（04の後）** | ✅ |
| ④ tougou-report | ✅ | 参考 | 参考 | **❌ 読まない** | ✅ |
| 人間 | ✅ | ✅ | 自分で書く | **現場から帰るまで見ない** | ✅ |

> **★`02` 末尾にも汚染源がある**（実走ログ 3-21）。
> 人間が現場後に書く「自分の見立て」は**結論**なので、②に見せると②が独立でなくなる。
> 一方③にとっては、`03`（AI）とも `04`（現場）とも独立した**3つ目の視点**なので見せてよい。
> **同じファイルでも、段によって見せる範囲が違う。** ここを間違えやすい。

> **★★`settings.json` の deny は、エージェントの立場を区別しない**（実走ログ 18-5・19-1）。
> `03_仮説_封.md`／`02b_主任診断士の見立て_封.md` の deny は、②のサブエージェントだけでなく、
> **③のサブエージェントも、この司令塔（あなた自身）も、一律に Read できなくする。**
> 「③・司令塔だけ読める」という区別は settings.json には存在しない。
>
> だから③にファイルパスを渡して「読んでください」と指示しても、③は開封できずに止まる
> （実際に起きた。deny を一時的に外せば読めるが、**settings.json は本人以外編集しない**と決めた）。
> → **③には、本人がコピーした `03`/`02b` の中身を、司令塔が事前の基準を外して（`strip_kijun.py`）プロンプトに直接埋め込んで渡す。**
> 詳しい手順は下の Stage 4。

## 手順

### Stage 0 ｜ どこから始めるかを見極める

> **★最初に、封が本当に効いているかを確かめる**（2026-11-26／クラウドの通しで、封もフックも効いていなかった）
>
> 封（`.claude/settings.json` の deny）とフック（`notice.py`・`seal_guard.py`）は、**Claude Code をこのリポジトリのフォルダで開いたときしか読み込まれない。**
> 別のフォルダで開くと、何の警告もなく全部外れる。`check_seal.py` は設定が書いてあるかを見るだけで、効いているかは見られない。
>
> 1. `案件/_封の確認/03_仮説_封.md` を作り（中身は1行でよい）、**Read ツールで開こうとする**
> 2. **拒否されれば封は効いている。** 確認用のフォルダを消して進む
> 3. **読めてしまったら、どの段も起動しない。** 本人に「Claude Code をこのフォルダで開き直す」よう伝える
>
> フックが効いていない環境でも①の出力の形だけは止まるよう、`check_anken.py` が `tests/card_checks.py` も流す（2026-11-26）。

案件フォルダの中身を `ls` して、**既にあるものの次から始める。** 作り直さない。

| 既にあるもの | 次にやること |
|---|---|
| 何も無い | Stage 1（①） |
| `01`〜`03` あり、現場メモ無し | **止まる。** 人間が現場に行くまで進めない |
| 現場メモあり、`04` 無し | Stage 3（②） |
| `04` あり、`05` 無し | Stage 4（③） |
| `05` あり、`06` 無し | Stage 5（④） |

**現場メモが無いのに②以降を回さない。** B軸の材料が無ければクロスは成立しない。

> **★どの段を起動する前にも、まずこれを実行する**（実走ログ #24）：
>
> ```
> python3 check_anken.py 案件/{社名}
> ```
>
> **NG が1件でも出たら、どの段も起動しない。** 検査するもの：
> 同一案件内の番号重複／禁止語彙（`_旧_` `_保留_` 等）／案件フォルダ内の隔離フォルダ／②③④が読む先の存在。
>
> **★これはルールではなく機械検査である**（文章で足した恒久ルールは翌日に破れた → #23）。
> **文章のルールは読まれなければ効かない。スクリプトは読まれなくても効く。**
> 番号重複の検査は**接頭辞の一覧に依存しない**（未知の接頭辞でも捕まる）。

> **★③を起動する前に、必ず次の2つを実行する**（実走ログ 20・21・案件D）：
> 1. `ls 案件/{社名}/04_現場分析.md` — **`04` が実在するか。** ①だけで終わっている案件に③をかけない
> 2. `python3 check_genba_mark.py 案件/{社名}/_材料/B_現場/現場メモ.md` — **B軸の4印（話者／いつ／どこで〈現地・遠隔〉／誰から〈直接・伝聞・書面〉）が揃っているか。****②の後は `python3 check_genba_ref.py 案件/{社名}/04_現場分析.md` も実行する**（`04` の根拠が、メモの【役割】の行を引いているか・その行の役割か・役割数が合うか → #58。B-1 の検証役より先）
>    ★**欄が埋まっているかだけでなく、中身の形も見る**（旧3印は `いつ・どこで | 2026-09-20` を通していた／B-4）。
>    NG が出たら③を起動しない。出所未確認のまま②③を回すと、後から「クロス分析として使えるか」を判定する手段が無くなる
>
> **①だけあれば②を起動してよい、とは限らない。** 現場メモ自体の出所も、②に渡す前に本人へ確認すること
> （②はメモの中身を分析するだけで、出所の妥当性までは判定しない）。

> **★出所未確認・汚染と判定して外すとき（→ 20〜23）：**
> 1. **`案件/_使わない/{案件名}_{日付}_{理由}/` に移す。**
>    **★案件フォルダの中に隔離フォルダを作らない。** 中に作ると、現役と同じ名前・同じ階層が
>    同じ案件の中に2つできる。人もAIも名前だけでは区別できず、必ず取り違える（実走22・23）
> 2. **中は平らにする。** `_材料/B_現場/` など現役と同じ階層を再現しない。
>    再現した瞬間、`_材料/B_現場/` への道が2本になり、本人が間違った方に保存する（→ 22・23）
> 3. **接頭辞は付けない。** `_保留_` `_旧_` は不要。`_使わない/` にある時点で使わない。
>    **場所で表す。名前で表さない。** 名前は付け忘れるが、場所は付け忘れられない
> 4. `_なぜ使わないか.md` に、何を・いつ・なぜ外したか書く
> 5. **★その場でチャットに全件報告する。** 動かしたファイルを1件ずつ。
>    実走ログに書くだけでは本人に届かず、本人の作業を混乱させる（実走22）
>
> **捨てない。** 比較すると直すべき箇所が見つかることがある。
> 規則の全文は `案件/_使わない/README.md`。

> **★`_旧_` を使わない（2026-09-20 決定）**
>
> AIが機械的に `_旧_` を付け、**内部用という別の文書**を古い版と取り違えた（→ CLAUDE.md §3）。
>
> **更新したら上書きする。前と今を両方作らない。**
> 本当に別物なら、別物の名前を付ける（例：`01` 提出用／`01i` 内部用）。
> **設計に無いものが生まれたら、`_旧_` を発明せず、設計に名前を足す。**
>
> **上書きしない例外は3つだけ：** `03_仮説_封` ／ `02b_..._封` ／ `01`・`01i`（現場前の凍結後）。
> これはクロス分析の成立条件そのもの（いつ封じたかが証明できなくなる）。
> エンジン側（`.claude/` 等）は git が履歴を持つので `.bak` を作らない。

### Stage 1 ｜ ① market-recon（A軸）

`.claude/skills/market-recon/SKILL.md` に従う。**これは自分（司令塔）が直接やってよい。**
①は最初の段なので、汚染される先がまだ存在しない。

終わったら必ず2つやる：

1. **`_材料/A_公開/取得ログ_{日付}.md` に生の材料を残す**
   取得URL・取得日・原文引用・**取れなかったもの**。
   → 後から `01` の記述を照合できる。AIは引用を捏造するし、**似た名前の別法人を誤同定する**
   （実走ログ 3-9）。生が残っていれば grep で捕まえられる。

2. **`01` に凍結宣言を書く**
   ```
   🔒 凍結日：{日付}（現場に入る前）／以後の追記は禁止（誤記の訂正のみ・履歴を残す）
   現場後の追加調査は `01b_現場後の追加調査.md` へ
   ```
   → 現場を見た後に公開情報を調べ直すと、それは「現場を知った目で選んだ公開情報」であり
   もうA軸ではない。`01` に追記した瞬間、`03` を封じた意味が消える（実走ログ 3-5）。

### Stage 2 ｜ ★報告する（ここが最も壊れやすい）

**`03` を作った直後の報告で、ほぼ必ず漏らす。** 実走ログ 1-8 で実際に漏らし、
その案件の主任診断士は**取り返しがつかない形で汚染された**。

**報告してよいもの**
- `01` の要点（事実のみ）
- `02` の問いの本数と分野
- 取れなかったもの・埋まらなかった項目
- **`03` は「n件作成した（未開封）」だけ**

**報告の粒度は、次に現場メモを書く人が誰かで変わる**（実走ログ 3-4）：

| 現場メモを書く人 | `03` の報告粒度 |
|---|---|
| **報告を読む本人**（＝ほとんどの場合） | **件数だけ。タグ内訳も伏せる** |
| 報告を読まない別人 | 件数＋タグ内訳まで |

> 「#財務 3」の一行だけで「財務に穴があるらしい」と伝わり、現場メモがそちらに寄る。
> **タグは方向そのもの。** 中身を書かなくても、方向を渡せば独立性は壊れる。

**❌ 禁止例（実際に起きたもの）**
- ❌「DXの空白という見立てを否定し、"使われていない可能性"に置き換えた」
- ❌「1件否定、2件削除、1件強化、5件新規」← 入れ替わりの説明が中身の説明になっている
- ❌「◯◯比率◯◯%という実数で根拠が強化された」

> **AIは「役に立とう」として要約したがる。この文脈では、要約が汚染そのもの。**
> 「何を見つけたか」を伝えたくなったら、それは封を破りたくなっているサイン。

### Stage 3〜5 ｜ ②③④は必ずサブエージェントで回す

**自分で `04`/`05`/`06` を書かない。** 理由はこのファイルの冒頭。

各段のプロンプト雛形は **`assets/subagent-prompts.md`** にある。そのまま使える。
渡すときは以下を必ず守る：

| 段 | 渡すもの | **渡さないもの** |
|---|---|---|
| ② genba-ops | **`01i`**／現場メモ／`02` 本文（ファイルパスを渡して読ませる） | **`03` の存在自体を伝えない**／`02b`／`01`（提出用） |
| ③ shinin-hansho | `04`→**`01i`**→`02` は**ファイルパスを渡して読ませる**。`02b`→`03` は**中身をプロンプトに埋め込む**（Stage 4） | 現場メモ（B軸は `04` だけで読む。②の取りこぼしは B-1 が見る → 75-15） |
| ④ tougou-report | `05`／**`01i`**／`04`（ファイルパスを渡して読ませる） | **`03`**（棄却された仮説がレポートに載る）／現場メモ（生の発言が④に入る。型に要る出所は「B軸の性質」で渡す → 63-5） |

> **★②③④が読むのは `01i`（内部用・定規）であって `01`（提出用）ではない**（2026-09-20 確定）。
> `01` は現場で相手に見せる紙であり、エンジンの入力ではない。
> 提出用は敬語と体裁のために食い違いが丸められる（「32名／35名／38人／40名 — 出典ごとに全部違う」が
> 「公式サイトには記載がありませんでした」になる）。**丸めた方を②に渡すと、②はズレを見つけられない。**

**サブエージェントには「読むな」ではなく「存在を知らせない」。** ②に対して
「`03` は読まないでください」と書くと、`03` があることを教えたことになる。
やむを得ず触れる場合は理由まで書く（雛形はそうしている）。

各段が終わったら、**報告に含まれる「詰まった箇所」を必ず受け取る。**（プロンプト雛形の最後にその指示が入っている。）**★②の後は、③の前に毎回 B-1 の検証役を走らせる**（`04` の根拠が現場メモにあるかを、別のサブエージェントに照合させる。雛形と手順は `assets/subagent-prompts.md` の「②の後」）。**「なし」「一部」が1件でもあれば③を起動せず、本人に見せる。**

### Stage 4 の詳細 ｜ ③に `03`/`02b` を「読ませず」に「渡す」（2026-09-19 改訂）

**背景（実走ログ 18-5・19-1）：** ③のサブエージェントに `03_仮説_封.md`／`02b_主任診断士の見立て_封.md`
をファイルパスで渡して「読んでください」と指示しても、**settings.json の deny に阻まれて開封できない。**
この deny はエージェントの立場（②か③か司令塔か）を区別しないため、**司令塔であるあなた自身も同じ理由で読めない。**
`settings.json` は本人以外編集しないと決めている（deny を一時的に外す運用はやめた）。

**だから、③には中身をプロンプトに直接埋め込んで渡す。** 取得は本人に頼む：

1. **②が完了していることを必ず確認してから**（②より前に頼むと②の独立性が壊れる）、
   本人に1つずつ頼む：「エディタで `案件/{社名}/03_仮説_封.md` を開き、全選択→コピーして『コピーした』と書いてください（貼り付けなくてよい）」。済んだら `02b_主任診断士の見立て_封.md` も同じように。司令塔は1つごとに `pbpaste | python3 .claude/skills/cross-run/scripts/strip_kijun.py` を回して中身を受け取る（heredoc で渡すと中身の「案件」と ** で seal_guard に止まりうる）
   （VS Code 拡張では `!` のコマンドは実行されず文字列だけが届き、`pbcopy` の案内も届かない → 実走 62-9。`!` が効くのは端末版だけ）
   （人間が直接開く分には deny も auto mode classifier も掛からない）
2. **受け取った中身の見出しの案件名が、今回の案件と一致するか照合してから**（案件ごとに同じ名前の `03` があり、エディタで開いていた別案件の `03` が2回届いた → 実走 62-3。違えば埋め込まず頼み直す）、事前の基準（〔当たり〕〜〔p〕）を外した後の中身を `assets/subagent-prompts.md` の③プロンプト内にそのまま埋め込む（10-03：③が p に引っぱられない・`05`→`06` に運ばない。`strip_kijun.py` が ✗ なら埋め込まず本人に知らせる）
   （ファイルパスとして渡すのではなく、プロンプト本文にテキストとして書き込む）
3. ③のサブエージェントには、`03`/`02b` が**ファイルとして存在すること自体を伝えない**。
   埋め込まれたテキストとして受け取るだけにする

**★司令塔（あなた）が `03`/`02b` の中身を会話に保持するのは、この受け渡しの間だけに限る。**
③に渡した後、必要以上にその内容を繰り返し引用したり、後続のやりとりで要約し直したりしない
（Stage 2 の「報告してよいもの」の原則と同じ理由）。

### Stage 6 ｜ 実走ログに全件書く

**これをやらないと、このスキルを使った意味がほぼ無い。**

`実走ログ.md` に、各段で出た詰まりを**全件**書く。

- **うまくいった話は要らない。詰まった話だけ書く。**「動きました」で終わらせると、次に同じ場所で詰まる
- 分類を付ける：`スキルの穴`／`テンプレの穴`／`手順の抜け`／`汚染`／`データの誤り`／`見立ての誤り`／`技術的限界`
- **直さないと決めたものも書く。** ❌ と理由を残す。次の人が同じ判断を繰り返さずに済む
- **配管として正しく動いたことも短く記録する**（順序が守られたか・棄却が漏れなかったか）。
  ここだけは例外。次に壊れたとき、何が壊れたのかを特定するための基準線になる

## 通し終わったあとの検算

出力を読んで、以下を実際に確かめる。**「そう書いてあるから」で済ませない。**

- [ ] `04` §0 に独立性の宣言があり、`03` 未読が明記されているか
- [ ] `05` §0 に開封記録があり、**`04` を先に読んだ**ことが書かれているか
- [ ] `06` に**棄却された仮説が載っていないか**（grep で棄却の特徴語を全文検索する）
- [ ] `06` の「要検証」が結論として書かれず、**問いに回っているか**
- [ ] **①だけでも②だけでも出ない結論が実際に出たか**（＝クロスが成立したか）。
      0件なら、それは「クロスをやったが何も出なかった」であって、記録に値する

### ★段ごとに正しくても、連鎖で壊れることがある

実際に起きた例（→ 3-48）：

> ③が「これは自分が新しく作った仮説だ」と自己申告し、対抗仮説を併記して人間に送った——正しい。
> **だが④はそれを課題の見出しに昇格させた。**

**各段の検査だけでは捕まらない。** 通し終わったら、③が「新規に作った」と申告したものが
④でどう扱われているかを、必ず目で追う。

## 判断に迷ったときの原則

- **不明は「不明」と書く。** 推測で埋めた瞬間、事実の顔をした仮説になる
- **断定しない。**「〜の可能性」「〜という仮説」。決着させると食い違いが持つ情報が消える
- **一般論を証拠にしない。** 業界パックもWeb検索の業界解説も当て木であって裏付けではない。
  現場がパックと食い違ったら**現場が勝つ**
- **最終判断はAIがしない。** ③は格付けまで。決めるのは人間
- **食い違いは方向とは限らない。** 実走では「結論は一致だが根拠・機序が食い違う」が最多だった
  （実走ログ 3-28）。「①がXと言い②がnot-X」だけを探すと見落とす

## 守秘

- 現場メモを外部検索・外部モデルに流さない
- `04` に生の逐語・個人名を書かない。**役割**（「保守担当リーダー」）と**頻度**だけ
- **顧客の実数を、スキル・業界パック・`STATUS.md` に書かない。**
  そこは push される。→ `client-data-firewall` スキルを併用する
- 案件フォルダを git で追跡しない
